# Техническое задание: AI-Analyst Bot (Analytics_bot)

Документ основан на локальных правилах проекта в `.cursor/rules/` (`architecture.md`, `ai_rag.md`, `scraper.md`, `observability.md`) и фиксирует целевую архитектуру, стек и требования к реализации.

---

## 1. Назначение и цели

**Назначение:** автоматизированная аналитическая платформа на базе бота и фоновых процессов: сбор данных из внешних источников, обогащение контекстом через RAG, генерация аналитических выводов с помощью LLM, доставка результатов пользователю через Telegram.

**Цели:**

- Обеспечить типобезопасный бэкенд на Node.js с чётким разделением модулей и оркестрацией сценариев в `pipeline/`.
- Обеспечить воспроизводимую инфраструктуру (PostgreSQL, при необходимости Redis) через Docker.
- Обеспечить наблюдаемость: структурированные логи, сквозные идентификаторы операций, безопасное логирование (без секретов и ПДн).

---

## 2. Технологический стек

| Слой | Технология |
|------|------------|
| Runtime | Node.js, TypeScript |
| HTTP API | Fastify с `fastify-type-provider-zod` |
| Валидация | Zod (схемы — первичный источник типов: `z.infer<typeof schema>`) |
| Бот | grammY; в production — webhooks |
| СУБД | PostgreSQL + расширение **pgvector** |
| ORM | Prisma |
| Инфраструктура | Docker, Docker Compose |
| Планировщик | `node-cron` |
| Git-автоматизация | Husky |
| Логирование | Pino, JSON-логи |
| Скрапинг / браузер | Playwright (headless) |

Разработка и запуск инфраструктуры БД (и Redis, если используется) — **только через Docker**.

---

## 3. Архитектура и границы системы

### 3.1. Слои и каталоги (`src/`)

| Каталог | Назначение |
|---------|------------|
| `core/` | Инициализация Fastify, Prisma, Bot API, глобальные плагины |
| `modules/` | Изолированные доменные блоки: `scraper`, `analyzer`, `rag`, `telegram` (и др. по мере роста) |
| `pipeline/` | Оркестраторы, соединяющие несколько модулей в единый сценарий |
| `schemas/` | Централизованные Zod-схемы |
| `tasks/` | Описание cron-задач (`*.task.ts`) — только триггер; бизнес-логика в `pipeline/` или `*.service.ts` |

### 3.2. Соглашения по именованию файлов

- `*.schema.ts` — Zod-схемы  
- `*.service.ts` — бизнес-логика  
- `*.provider.ts` — внешние API, скраперы, интеграции  
- `*.handler.ts` — обработчики бота  
- `*.task.ts` — точка входа cron-задачи  

### 3.3. Типизация

- **Zod first:** сначала схема, затем логика; типы выводятся из схем.  
- **`any` в бизнес-логике запрещён.** На внешних границах (SDK, legacy) допускается работа через `unknown` с явным сужением типа и комментарием причины.

## 4. Функциональные требования по подсистемам

### 4.1. Telegram-бот (grammY)

- Реакция на пользовательские события через обработчики (`*.handler.ts`).
- Production: работа по **webhooks** (требование к развёртыванию и конфигурации окружения).

### 4.2. Модуль скрапинга (Playwright)

- **Изоляция:** в `providers/` — один сайт/источник — один провайдер.
- **Валидация выхода:** любые данные из браузера перед возвратом из модуля проходят `.parse()` соответствующей Zod-схемы.
- **Ориентация на Cron:** без ручных шагов (капча, интерактив); повторные попытки при сетевых сбоях с backoff и jitter; явные таймауты навигации/ожиданий и общий таймаут задачи.
- **Жизненный цикл браузера:** `try / catch / finally`; в `finally` — обязательный `await browser.close()` для предотвращения утечек в Docker.
- **Устойчивость:** ошибка парсинга отдельного поля/страницы не валит весь процесс — локальная обработка и продолжение.
- **Режим:** по умолчанию `headless: true`.
- **Stealth:** разумные заголовки и эмуляция для снижения риска блокировок при автозапусках.
- **Логи:** старт/финиш провайдера, число сущностей, причины частичных сбоев с `jobId`.

### 4.3. AI, эмбеддинги и RAG

- **Роли моделей (не хардкод версий в коде):**
  - `PRIMARY_REASONING_MODEL` — финальный аналитический вывод, сложные цепочки.
  - `LONG_CONTEXT_MODEL` — первичная обработка больших объёмов и длинного контекста.
- Идентификаторы моделей задаются через **env/config**, смена модели без правок кода.
- Системные промпты и инструкции хранятся в `src/modules/analyzer/prompts/`.
- **Конвейер анализа:** `Данные → эмбеддинг → RAG (поиск контекста) → LLM → финальный результат`.
- **Векторный поиск:** PostgreSQL + Prisma + pgvector; для операций векторного сходства использовать `Prisma.$queryRaw` с **параметризованными** запросами (без интерполяции пользовательского ввода в SQL-строку).
- **Оператор сходства:** косинусное расстояние через оператор `<=>`, например: `ORDER BY embedding <=> $1::vector`.
- **Ответы LLM:** при структурированном JSON-ответе — валидация через Zod.
- **Надёжность LLM:** retry/backoff и поведение при деградации (запасная модель или упрощённый режим).

### 4.4. Планировщик (Cron)

- В `*.task.ts` — только триггер; логика в `pipeline/` или сервисах.
- **Безопасность выполнения:**
  - обязательный `timeout` на уровне задачи;
  - запрет параллельных дублей одной и той же задачи (один активный инстанс);
  - логирование жизненного цикла: старт, успех, ошибка с контекстом.

### 4.5. HTTP API (Fastify)

- Маршруты и входные данные согласованы с Zod (type provider).
- Ошибки API — в духе observability: контекст, без утечки секретов.

## 5. Данные и хранение

- Основное хранилище: **PostgreSQL** с **pgvector** для векторного поиска.
- Доступ к данным через **Prisma**; сырые vector-запросы — через `$queryRaw` с параметрами.

*(Схемы таблиц и миграции не зафиксированы в правилах — уточняются отдельным проектным решением и Prisma schema.)*

---

## 6. Наблюдаемость, логи и ошибки

- Логи — **только структурированный JSON** (Pino / интеграция с Fastify).
- В pipeline и cron каждая операция должна иметь **`jobId`** или **`requestId`** / **`traceId`** для сквозной трассировки.
- Ошибки логируются с входными данными (без sensitive data) и стеком.
- **Запрещено** логировать токены, пароли и персональные данные.
- Ошибки оборачиваются в понятный контекст (например, привязка к сущности по ID).
- В циклической обработке (скрапинг списков) сбой одного элемента не останавливает весь цикл — частичный сбой логируется, обработка продолжается.

---

## 10. Критерии соответствия реализации

Реализация считается соответствующей целевой архитектуре, если:

1. Соблюдена структура `src/` и соглашения по именованию слоёв.  
2. Валидация и контракты данных опираются на Zod; типы выведены из схем.  
3. Cron-задачи изолированы в `tasks/`, с таймаутом, защитой от дублей и полным логированием жизненного цикла.  
4. Скрапер использует провайдеры, Zod на выходе, headless Playwright, гарантированное закрытие браузера и устойчивость к частичным сбоям.  
5. RAG и анализ следуют цепочке данных → эмбеддинг → поиск → LLM; vector-поиск безопасен по SQL; модели конфигурируются через env.  
6. Логи JSON, с `jobId`/`requestId`/`traceId` где требуется, без секретов и ПДн в открытом виде.  
7. Husky pre-commit выполняет lint-staged и `tsc --noEmit`.  
8. Инфраструктура БД для разработки поднимается через Docker.
